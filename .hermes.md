# Project Orchestration Rules

This workspace is managed through a multi-agent development workflow.

## Agents

- Orchestrator: plans, decomposes, coordinates, tracks state, and reports.
- Coder: implements approved tasks.
- Reviewer: independently reviews and tests completed work.

The Orchestrator should normally not write production code directly.

## Persistent Project State

Before planning significant work, inspect:

- `PROJECT_STATE.md`
- `CURRENT_PLAN.md`
- `DECISIONS.md`

These files are durable project memory and must be kept synchronized with actual project state.

Do not rely on conversation history as the primary source of truth.

## Context Discipline

Prefer:
- targeted repository searches
- git diffs
- specific relevant files
- concise worker summaries

Avoid:
- loading the entire repository without need
- copying large terminal logs into context
- storing conversation transcripts as project memory

## Workflow

For non-trivial development work:

1. Understand the user's goal.
2. Inspect persistent project state.
3. Inspect only relevant repository context.
4. Update the plan.
5. Delegate implementation to the Coder.
6. Send completed changes to the Reviewer.
7. If review fails, return actionable feedback to the Coder.
8. Re-plan if the problem is architectural rather than implementation-only.
9. Update persistent project state after meaningful progress.
10. Report status and results to the user.

## Completion

A development task is not complete until required tests and independent review have passed.

## Checkpointing

Before a long session ends or context becomes large:

- update `PROJECT_STATE.md`
- update `CURRENT_PLAN.md`
- record important decisions in `DECISIONS.md`
- preserve blockers and unresolved risks
- ensure active tasks contain enough context for a fresh Orchestrator session to continue
